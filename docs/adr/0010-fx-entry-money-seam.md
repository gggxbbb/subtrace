# 外币录入：统一金额缝与服务端兜底

涉钱录入（付费记录、物品买入、追加费用、收益、联合会员打包实付、订阅标准价）统一为「金额三件套」：原币金额 + 币种 + 主币种快照。客户端收敛为单个金额录入组件（内置汇率预填），服务端收敛为单个解析函数，按显式决策树兜底：

- 币种为空或等于主币种 → 快照 = 原币金额（正当 1:1）
- 币种 ≠ 主币种且手填了折算 → 用手填值（ADR-0004 快照哲学：录入即事实）
- 币种 ≠ 主币种、折算留空、汇率表有此币对 → 服务端查汇率表计算（两位小数）
- 币种 ≠ 主币种、折算留空、汇率表无此币对 → **拒绝提交**，显式报错（error=fx），不再静默 1:1

展示层金额格式化跟随用户主币种（取代 v1 全站硬编码 CNY）。订阅标准价升级为三字段（原币 + 币种 + 主币种快照），与付费记录同构。金额未知（ticket 12）语义不变：付费记录金额留空则三字段全 null。

原因：对本仓库 13 个涉钱表单的审计发现同一概念碎成多种残缺形态——订阅向导/编辑表单的「标准价」输入直接写入主币种快照字段却旁挂币种选择器（语义错位误导）；向导首笔付费与联合会员打包实付有币种无折算框；追加费用/收益表单无币种无折算（CNY-only）；所有 server action 以 `?? amount` 静默 1:1 兜底，汇率表缺币对时错误快照无警告落库；按字段名硬匹配的预填脚本天然接不上带前缀的字段（firstAmount 等）。

## Considered Options

- 维持 1:1 兜底但打标记：需引入全局「估算快照」概念（schema + 引擎 + 展示都要认识它），为边缘场景加全局复杂度，被否。
- 快捷表单（追加费用/收益）保持 CNY-only 单框：放弃外币场景，且与付费表单两种模式并存，违反「一个概念一个模式」，被否。
- 纯客户端预填、服务端不兜底：预填可被绕过（禁用 JS、直写提交），服务端无不变量则错误数据始终可能落库，被否。

## 关系与后果

- 延伸 ADR-0004：快照哲学不变（改汇率不回溯历史），但「快照必须有据」——来自汇率表或用户手填，不再凭空 1:1。
- 存量按 1:1 落库的记录不回填（快照即当时事实）；用户可经编辑表单修正，编辑路径同样走新决策树。
- 提交多一种失败形态（error=fx）：用户出路为「设置→汇率」配币对，或当场手填折算金额。
