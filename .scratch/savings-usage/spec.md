# 省钱型用量口径（折扣类会员）

Status: ready-for-agent

Grilling 产出：决策全文见 ADR-0011 与 CONTEXT.md「用量 / 联合会员 / 替代单价」三处词条（2026-07-31）。

## Problem Statement

京东 Plus、88VIP、盒马 X 这类折扣类会员的价值不体现在"用了多少次"，而体现在"买东西时省了多少钱"——立减、返现、免运费券，平台会员页直接给出"当期已省 xxxx"。现有两种用量口径都不适配：计数型要求固定替代单价，但每单省的钱不固定，且平台已经直接算好了金额，换算成"次数 × 平均单价"反而丢掉真值；额度型则根本没有额度概念。结果是这类会员在系统里只有成本、没有获益记录，盈亏面板与红黑榜对它们沉默，"这个会员买得值不值、续不续"没有判据。88VIP 更尴尬：按 ADR-0002 它是联合会员，打包费被优酷/网易云等子会员按比例摊满后，折扣权益成本为零，即使记了省钱也盈亏恒正，判据同样失效。

## Solution

新增第三种用量口径「**省钱型**」：记录的用量就是省下的金额本身（主币种）。订阅详情的录入卡支持两种姿势：直接填"本次省了 ¥6"（增量），或照抄平台"当期已省 ¥342"（自动与上一条累计值求差转增量）。盈亏面板显示 盈亏 = Σ已省 − 已摊成本，辅以回本差额（还差 ¥X 回本 / 已净省 ¥X），不显示每次实际成本；dashboard 红黑榜照常按盈亏排序。联合会员中的折扣权益（88VIP 的淘宝折扣）走现有两步流：建联合会员时把它加为一个子会员并**手填分摊额**（向导已有「分摊额（可改）」字段），再到该子会员详情设为省钱型——成本基由用户按"我为什么买它"主观分配，盈亏判据由此成立。

## User Stories

1. 作为用户，我想把订阅的用量类型设为「省钱型」（向导第三张卡，含适用场景说明：京东 Plus / 88VIP / 盒马 X），以便折扣类会员也能追踪盈亏。
2. 作为用户，我想省钱型不需要填单位、替代单价、总额度，以便录入配置不比必要信息更复杂。
3. 作为用户，我想直接录入一笔"本次已省"金额（这单运费券抵了 ¥6），以便随用随记。
4. 作为用户，我想照抄平台"当期已省"累计值，由系统自动与上一条累计值求差存为增量，以便不用手算差额。
5. 作为用户，当求差结果 ≤ 0（如会员期重置导致平台累计归零）时，我想被明确拒绝并提示改用增量录入，以便不产生静默的负省钱。
6. 作为用户，我想在录入卡看到上一条累计值作参考，以便照抄平台数字时知道基准。
7. 作为用户，我想在用量记录页查看、编辑（日期/金额）、删除省钱记录（标签为「已省金额」），以便记错能改。
8. 作为用户，我想盈亏面板显示当前区间盈亏 = Σ已省 − 已摊成本，以便回答"回本没有"。
9. 作为用户，我想看到回本差额（未回本时"还差 ¥X 回本"，已回本时"已净省 ¥X"），以便续费决策有直观依据。
10. 作为用户，我想省钱型不显示"每次实际成本"，以便指标不与省钱语义冲突。
11. 作为用户，我想历史区间可回看省钱盈亏（与计数/额度型一致），以便复盘上一个会员年。
12. 作为共享会员的所有者，我想各受益用户各自录入自己的已省金额（家庭共用京东 Plus，谁下单谁记），以便看到谁在用、谁纯享折扣。
13. 作为所有者，我想详情页按受益人切片显示省钱盈亏（成本 × 份额、用量只计本人），以便分摊视角与计数/额度型一致。
14. 作为用户，我想 dashboard 红黑榜把省钱型订阅按盈亏纳入排序（亏损标红），以便折扣会员与其他订阅同榜比较。
15. 作为用户，我想为 88VIP 建联合会员时把「淘宝折扣权益」加为子会员并手填分摊额（如 ¥40），再设为省钱型，以便折扣权益有成本基、盈亏判据成立。
16. 作为用户，我想单独购买的京东 Plus 直接设为省钱型并录入已省，以便独立折扣会员全流程闭环。
17. 作为用户，我想已省金额以主币种记录（录入即快照，ADR-0004 哲学），以便改汇率不影响历史盈亏。
18. 作为信任用户，我在脚本管理页只看到额度型订阅（省钱型不出现），以便不会误以为能脚本抓已省（ADR-0011：本次不开放）。

## Implementation Decisions

- **Schema**：`Subscription.usageKind` 新增 `"SAVINGS"` 值。SQLite 中该列为 TEXT 无枚举约束，**无需迁移**。省钱型不使用 `usageUnit` / `altUnitPrice` / `quotaTotal`（置空）。
- **UsageRecord**：省钱型记录固定 `kind=DELTA`、`source=MANUAL`；`quantity` = 已省金额（主币种）；`unitPrice` / `quotaTotal` 置空。
- **引擎**：`usageInPeriod` 的 DELTA 增量求和路径零改动；省钱型盈亏即 `verdict(costShare, saved, 1)`，可新增语义化别名 `savingsVerdict(costShare, saved) = saved − costShare`；回本差额 `= costShare − saved`（正 = 还差多少回本）。`actualCostPerUse` 不用于省钱型。
- **用量服务**：新增 `addSavings(actorId, subscriptionId, userId, {date, amount? , cumulative?})`——amount 与 cumulative 二选一必填；cumulative 时取该订阅该用户最新一条省钱记录求差，`diff ≤ 0` 拒绝并提示改用增量录入；守卫 `usageKind === "SAVINGS"`；录入权限复用现有 `assertUsageAllowed`（所有者或 USER 受益人）。编辑/删除复用 `updateUsage` / `deleteUsage`（编辑仅允许改日期与金额）。
- **判定装配**：`getUsageVerdict` 返回新变体 `SavingsVerdict`（`kind: "SAVINGS"`、已摊成本、Σ已省、盈亏、回本差额、成本未知标记）；受益人切片复用现有 `forUserId` 机制。
- **UI**：用量向导加第三张卡（省钱型：定义 + 适用例子，无额外字段）；用量录入卡加省钱型分支（两个录入姿势：本次已省 / 平台累计自动求差，显示上一条累计值）；盈亏卡加省钱型分支（盈亏 + 回本差额，隐藏每次成本）；用量记录页金额列标签「已省金额」。
- **联合会员**：零改动——手填分摊额（`allocatedBase`）在向导与 `materializeItems` 中已存在且有测试覆盖；spec 层面的"折扣权益子会员"是用法不是新机制。
- **Dashboard**：红黑榜按 verdict 值纳入现有排序，省钱型无特殊分支。

## Testing Decisions

好测试标准：只测外部行为（服务返回值、落库状态、判定输出），不测实现细节；沿用仓储缝测试风格（真实 prisma 测试库，fileParallelism: false）。

- **引擎缝**（`cost-engine` 纯函数测试）：`savingsVerdict` 盈亏与回本差额（含未回本/已回本/零成本基）；`usageInPeriod` 增量路径已有覆盖，不重复。先行例子：`index.test.ts` 的 verdict / allocateBundle 用例。
- **用量服务缝**（prisma 测试库）：`addSavings` 守卫（非省钱型拒绝、无权用户拒绝）；增量落库（DELTA/MANUAL、单价与额度置空）；累计录入自动求差（含基于上一条的差值正确性）；求差 ≤ 0 拒绝；`getUsageVerdict` 省钱型变体装配（盈亏 = Σ已省 − 已摊、受益人按 userId 切片、金额未知段标记）；红黑榜数据源纳入省钱型。先行例子：ticket 06 用量服务 6 条仓储缝测试（健身房 9×30−217=53）、`bundles/service.test.ts`。
- **冒烟**：dev server 起服务，浏览器走"京东 Plus 设省钱型 → 增量录入 → 累计录入求差 → 盈亏/回本差额显示 → 红黑榜出现"全流程。

## Out of Scope

- 省钱型用量脚本（ADR-0011 已决：已省数据在登录墙后且有反爬，暂无可行抓取方案；未来可行时再扩脚本准入集合）。
- 联合会员向导内嵌用量类型选择（两步流"建子会员 → 详情页设省钱型"可接受）。
- 平台"已省"数字的口径校验与去水分（信任用户输入，录入即事实）。
- 物品受益人的省钱记录（物品不下单；受益人切片按 userId，天然不涉及）。
- 退单扣回已省（负增量录入）——求差拒绝策略同样挡住，需要时另议。

## Further Notes

- 会员期重置导致平台累计归零是预期场景：求差被拒后改用增量录入，数据等价。
- 88VIP 手填分摊额是主观分配（"我主要为折扣买它 → 摊 ¥40"），这是特性不是缺陷——成本基的主观性恰是退订判据的输入。
- 与并行 spec（led-matrix-responsive、dark-mode、ui-hardening）无文件冲突面。
